# AI_REVIEW

## 1. Использованные AI-инструменты

- **Claude** (Anthropic), модель Claude Sonnet 5.5, веб-интерфейс claude.ai. Использовались чат,
  веб-поиск Claude (для проверки версий и известных проблем), создание файлов в сессии.
- Других AI-инструментов (Copilot, ChatGPT и т.п.) не использовалось.

## 2. Как строилась работа

Задание делалось поэтапно в одном диалоге. Схема каждого этапа одинакова:

1. Claude предлагает небольшой фрагмент (команды, compose-файл, код Dagger-функции).
2. Я выполняю его на своей машине (Arch Linux, Docker 29.9.2, Dagger v0.21.11) и вставляю в чат
   вывод терминала целиком, в том числе ошибки.
3. По фактическому выводу Claude подтверждает результат или исправляет решение.

Все утверждения AI о версиях и поведении инструментов проверялись реальным запуском. Решение «работает»
только тогда, когда я видел это в выводе своего терминала. Итоговую работоспособность подтверждает
запуск `dagger call deploy-all` с чистого стенда (около 1,5 минут, все проверки `validate` проходят).

## 4. Примеры некорректных, устаревших и неоптимальных решений AI

### Пример 1. Устаревшая версия cAdvisor падает на Docker 29

**Что предложил AI.** Образ `ghcr.io/google/cadvisor:0.56.1`: версию AI взял из найденного гайда за март 2026,
где она названа «latest release».

**Как обнаружил.** Контейнер стартовал и тут же падал с `panic: nil pointer dereference` в
`container/docker/handler.go` (стек в `docker logs`). `docker info` показал `driver-type: io.containerd.snapshotter.v1`:
в Docker 29 хранилище образов containerd включено по умолчанию, и cAdvisor 0.56.1 не умеет работать с таким
контейнером (у него нет GraphDriver).

**Как исправил.** Поиск по issue и changelog cAdvisor нашёл исправление «docker: fix nil pointer dereference when
GraphDriver is nil» в версии 0.56.2. Проверил обе версии, 0.56.2 и 0.60.3: обе стартуют, в метриках видны
имена контейнеров (`kuma-mariadb`, `kuma-uptime-kuma`). Выбрал 0.60.3 и закрепил в compose.
Рекомендованное в одном из гайдов отключение `containerd-snapshotter` в `/etc/docker/daemon.json` отклонил:
оно меняет глобальные настройки Docker и не сработает на машине проверяющего.

### Пример 2. Ошибка импорта дашборда не проваливала команду

**Что предложил AI.** Первая версия `configure-grafana` отправляла дашборд конвейером
`jq ... | curl ... | jq -c ...`. Последней командой конвейера был `jq`, поэтому даже при ответе Grafana с ошибкой
команда завершалась с кодом 0 и выглядела успешной.

**Как обнаружил.** При ревью кода перед написанием `deploy-all`: результат функции должен быть пригоден как
критерий готовности платформы, а у этой функции его не было. Ошибку сначала увидел AI, перечитывая свой код,
затем я проверил логику по скрипту.

**Как исправил.** Ответ API сохраняется в переменную (`resp=$(... | curl --fail-with-body ...)`, код возврата
`curl` проваливает скрипт при `set -e`), затем явно проверяется `.status == "success"`. Аналогично проверяется
health датасорса. Итоговая валидация (`validate`) отдельно проверяет, что дашборд реально существует в Grafana.

### Пример 3. Непроверенные гипотезы AI, отброшенные по фактам

AI дважды выдвигал предположения, которые не подтвердились первой же проверкой:

- **Флаги cAdvisor `--containerd=... --containerd-namespace=moby`** (из статьи про Docker 29). Контейнер работал,
  но в метриках вместо имён были 64-символьные идентификаторы, то есть дашборд был бы бесполезен.
  Отброшено, после чего нашлось исправление из примера 1.
- **Гипотеза «TLS-таймауты до Docker Hub из-за MTU туннеля».** Проверка (`ip link`) показала MTU 1500 на всех
  интерфейсах, а с хоста 5 из 5 запросов к `auth.docker.io` прошли с кодом 200. Гипотеза не подтвердилась;
  сбои оказались плавающими и снимались повтором команды (это отражено в README).
- **Диагностическая команда с `wget` внутри контейнера Dagger Engine**: в его образе нет `wget`,
  команда была некорректной.

Вывод: гипотезы AI о причинах я проверял по фактическому выводу, и ни одна из этих трёх не попала в итоговое решение.

### Пример 4. Изменяемый тег образа `docker:cli` ломал повторные запуски

**Что предложил AI.** Использовать в модуле образ `docker:cli` по плавающему тегу.

**Как обнаружил.** Повторные вызовы `dagger call` периодически падали ошибкой
`failed to resolve image "docker.io/library/docker:cli" ... HEAD ... TLS handshake timeout`, хотя образ уже был
скачан: по плавающему тегу движок заново обращается к реестру, и любой сетевой сбой ломает запуск.

**Как исправил.** Закрепил образ по digest (`docker@sha256:...`), так запуск становится воспроизводимым и
не зависит от повторных запросов к реестру за манифестом. Оговорка: я не изолировал эффект от закрепления,
то есть не доказал, что оно было единственной причиной сбоев. Сбои до Docker Hub плавающие, и в README
для них описан повтор команды.

### Пример 5. `docker kill` не запускает restart-policy

**Что предложил AI.** В задании chaos-тест формулируется как остановка контейнера `docker stop` с проверкой возврата
по restart-policy. AI сразу указал на противоречие (Docker не перезапускает вручную остановленные контейнеры) и предложил
два режима: `stop` для проверки дашборда и `crash` для проверки политики. Но падение для режима `crash` он реализовал
через `docker kill`, предположив, что политика сработает. AI сам пометил это как неуверенное предположение, но всё равно
заложил его в код.

**Как обнаружил.** Первый запуск `dagger call chaos` упал с `FAIL: (б) restart-policy не перезапустила kuma-uptime-kuma за 60 с`
(`RestartCount` не вырос). Второй запуск (для `kuma-mariadb`) упал на предусловии: тест не убирал за собой, и Kuma после
первого провала так и осталась убитой. Кроме того, в фазе `stop` тест показывал «ВСЁ ПЛОХО через 0 с»: таймер стартовал
после `docker stop`, который сам занимает несколько секунд.

**Как исправил.** Поиск по обсуждениям moby и ответам на Server Fault показал: Docker считает `docker kill` ручной остановкой,
и restart-policy на такой контейнер не действует; падение нужно имитировать сигналом процессу по PID хоста в обход
Docker API. Теперь процесс убивается `SIGKILL` через одноразовый контейнер с `--pid=host`. Результат на обоих контейнерах:
`RestartCount 0 -> 1`, контейнер возвращается за 0–1 с. Добавлена очистка при любом выходе (контейнер возвращается в
работу) и таймер от начала `docker stop`.

## 5. Что проверялось руками

- Запуск `deploy-all` с чистого стенда (оба слоя снесены): все блоки и `validate` проходят, около 1 мин 13 с.
- Идемпотентность: повторный `deploy-all` и `configure-grafana` (датасорс: сначала `POST`, затем `PUT`).
- Отсутствие кэширования: `docker stop kuma-uptime-kuma`, затем `dagger call deploy-app` реально перезапускает контейнер.
- Сохранность данных: после `down` без `-v` Uptime Kuma и MariaDB поднимаются с прежними данными.
- Все 22 запроса дашборда возвращают данные (прогон по JSON через API Prometheus).
- Chaos-тест (`dagger call chaos`) для `kuma-uptime-kuma` и `kuma-mariadb`, оба режима: красный статус через 12–15 с
  после начала `docker stop`, возврат в зелёный за 7–10 с после `docker start`; при падении процесса (SIGKILL по PID хоста)
  restart-policy возвращает контейнер за 0–1 с (`RestartCount 0 -> 1`). Окно «ВСЁ ПЛОХО» при падении короче интервала
  сбора метрик (15 с) и на дашборд не попадает.
- Версии образов закреплены; после закрепления `validate` и chaos проходят.
- Архитектурное допущение AI о том, что `build:` работает из контейнера Dagger, а bind-mount нет, подтвердилось запуском.
